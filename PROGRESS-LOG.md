## Project 1.4 - Remote state and locking (S3 + DynamoDB) ✅ Complete

**Built:** `~/terraform-portfolio/project-1.4` - an `aws_s3_bucket` (`tf-portfolio-ajw-20260907`) to hold state, `aws_s3_bucket_versioning` enabled on it (safety net for state history), and an `aws_dynamodb_table` (`terraform_portfolio_locks`, `PAY_PER_REQUEST` billing, `LockID` hash key) for locking. Built with local state first (chicken-and-egg: Terraform can't store its own state in a backend that doesn't exist yet), then migrated this same project onto the S3 backend it had just created - direct hands-on contrast to the HCP-managed remote state from the HashiCorp tutorial (same underlying job - shared state storage + locking - but self-managed this time, seeing exactly what a platform like HCP is doing under the hood).

**Real debugging done independently:**
- Traced a misplaced `resource` block accidentally nested inside `required_providers` (confusing a provider *declaration* with an actual resource block), and a subsequent brace-count error where one extra `}` closed the whole `terraform {}` block prematurely, pushing `backend "s3" {}` outside where it's valid - both fixed by careful brace-tracing, same technique as 1.3
- Hit and understood a genuine `No valid credential sources found` error at the backend level - root cause: **backend configuration authenticates separately from the provider block**, so `profile = "portfolio"` had to be added explicitly to the `backend "s3" {}` block too, not assumed inherited from `provider "aws" {}`. Directly parallels the earlier HCP tutorial lesson about local CLI profiles not carrying over to remote execution - same underlying principle (auth contexts don't automatically share) recurring in a different form.
- Noted (but correctly left unresolved, as informational) a live deprecation warning: `dynamodb_table` parameter is being superseded by `use_lockfile` in newer Terraform/AWS-provider versions, which drops the separate DynamoDB table requirement entirely in favour of a lockfile inside S3 itself - good awareness that the "S3 + DynamoDB" pattern, while still extremely common in existing/real codebases, is not the final word on this mechanic.

**The actual migration:** ran `terraform init` after adding the backend block, correctly identified (before answering) that "copy existing state to new backend? yes/no" was asking whether to preserve continuity with 3 already-real AWS resources, answered `yes` correctly, and confirmed the migration genuinely worked via three independent checks: local `.tfstate` files still present but now inert, the real state object visible directly in S3 via `aws s3 ls`, and `terraform plan` returning "No changes" when reading exclusively from the new remote location.

**Genuine, reproduced lock conflict:** added a `time_sleep` resource (`hashicorp/time` provider) purely to create a large enough window to test locking for real. Ran `apply` in one terminal, and while it was mid-flight, ran `plan` in a second terminal pointed at the same backend - got a real `ConditionalCheckFailedException` from DynamoDB, with Terraform's `Lock Info` block correctly identifying who held the lock and what operation they were running. Confirmed the lock released automatically once the first apply completed, and the second terminal's `plan` then succeeded cleanly. This is a strong, genuinely first-hand interview story - not just describing what locking does, but having deliberately reproduced the actual failure mode it prevents.

**Real-world gotcha hit and resolved: destroying a self-hosted backend while it's still active.** Running `terraform destroy` destroyed the DynamoDB table successfully, but then failed to delete the S3 bucket (`BucketNotEmpty`) - because bucket versioning (enabled deliberately as a safety feature) meant every past state-file write left a retained version behind, and S3 refuses to delete a bucket containing any object versions regardless of `force_destroy`. Terraform then also failed to release its own state lock afterward, since the DynamoDB table recording that lock had already been destroyed moments earlier - a genuine chicken-and-egg failure in reverse. **Root cause understood, not just patched:** you generally shouldn't destroy backend infrastructure while a project is still actively configured to use it as its backend - the correct pattern is migrating state back to local (or elsewhere) first, then destroying the now-unused backend resources freely, avoiding this exact ordering problem. **Resolved manually** via direct AWS CLI calls: listed and batch-deleted all three retained object versions, separately deleted a leftover delete-marker from an earlier partial cleanup attempt, then successfully deleted the empty bucket. Confirmed via `aws s3 ls` that no trace of the bucket remains.

**Why DynamoDB was chosen deliberately over the newer `use_lockfile` approach, despite the extra moving part:** `use_lockfile` (a `backend "s3" {}` argument, not a resource - achieves locking via an atomic write directly inside the state bucket itself, no second AWS service needed) is genuinely simpler and is where the tooling is heading, but it's new enough that most *existing* real-world Terraform codebases, documentation, and interview material still use the DynamoDB pattern - so building and genuinely troubleshooting the DynamoDB approach first was the more broadly useful thing to actually understand hands-on right now. Deliberately deferred trying `use_lockfile` hands-on as a quick follow-up exercise (delete the `dynamodb_table` backend line + the `aws_dynamodb_table` resource entirely, add `use_lockfile = true`, and observe `plan` proposing the now-orphaned DynamoDB table for destruction) - worth returning to at some point as a fast, low-effort comparison once the DynamoDB pattern is solid.

Directory-per-environment avoids this by keeping environments in physically separate files, at the cost of maintaining multiple file sets - a cost real teams typically absorb by pairing directory-per-environment with a shared **module** (directly connecting back to Project 1.5), so the common pattern lives once and each environment directory just calls it with different inputs. # PHASE 2.3 - DOCUMENTED, NOT DEPLOYED

Real `.tf` written and validated for each pattern below, deliberately never applied - all three genuinely require an AWS Organization (multi-account structure) that Free Tier's single-account setup cannot provide. `terraform validate` and `terraform plan` were run for each to confirm the HCL is structurally correct; `apply` was never run, and each entry below states what the real AWS API rejection would be, understood conceptually rather than tested, since `plan` only validates HCL structure and does not check account-level deployability - that gap only closes at `apply`, against the real API.

## 2.3a - Service Control Policy (SCP): deny root account usage

**Design:** an `aws_organizations_policy` resource (note: SCPs aren't a distinct resource type - they're one `type` value, `"SERVICE_CONTROL_POLICY"`, of the generic Organizations-policy resource) implementing a genuinely common real-world guardrail: denying all actions (`Action = "*"`, `Effect = "Deny"`) specifically when the requester's `aws:PrincipalType` condition key equals `"Root"` - blocking root-user activity account-wide, regardless of any IAM policy, boundary, or role permission anyone might otherwise have. Deliberately built to reinforce the scope distinction from Project 2.2's permission boundary: a boundary caps one specific IAM entity (attached directly to that user/role); an SCP caps an entire account or OU, with no `Principal` needed in the policy at all, since it applies to everyone and everything in scope by default - the `Condition` here narrows "everyone" down to "root specifically," rather than narrowing "who's allowed," which was the trust-policy job in every other resource built so far.

**Genuinely deep nesting, handled correctly on the first attempt** - five layers (resource → `jsonencode` → `Statement` list → statement object → `Condition` → `StringLike`), the deepest structure in the whole portfolio, written correctly without the multi-round correction 2.2's boundary policy needed. A real, useful confusion was surfaced and resolved along the way: raw JSON notation (`"Action": "*"`, used when explaining the *concept*, matching how AWS's own docs/console display policies) versus HCL notation (`Action = "*"`, what's actually typed in a `.tf` file) - worth remembering as two valid, different representations of the same policy, not a contradiction.

**`terraform validate`**: passed cleanly. **`terraform plan`**: passed cleanly, proposing `1 to add` - confirmed this only proves the HCL is well-formed, not that the resource is deployable; the real, expected rejection point would be `apply`, where AWS's Organizations API would return something like `AWSOrganizationsNotInUseException`, since no Organization exists in this Free Tier account for the policy-creation call to attach to.

## 2.3b - Cross-account role assumption

**Design:** an `aws_iam_role` with a trust policy identical in structure to every role built throughout this portfolio (1.3, 1.5, 2.1, 2.2's underlying pattern) - the *only* substantive change is the `Principal`'s `AWS` value: a fictional external account (`arn:aws:iam::999999999999:root`) in place of this portfolio's own account, since only one real AWS account exists to test against. Deliberately used to reinforce that cross-account assumption isn't a distinct mechanism requiring new resource types - it's the exact same trust-policy shape already mastered, with one value changed to point outside the account rather than within it. Real-world use noted as the actual mechanism that makes multi-account AWS environments usable day to day (one account's identity temporarily operating with another account's permissions via `sts:AssumeRole`).

**Real debugging, twice, on the same underlying mistake** - worth recording honestly: `Principal` was first written as a bare string rather than the required `{ AWS = "..." }` nested object (missing a layer, same "list vs. object wrapper" confusion pattern seen in earlier projects), corrected in reasoning but the actual fix wasn't saved to disk on the first attempt - `terraform validate` then failed with a genuine `Invalid expression` parse error pointing at the `Statement` list's closing bracket, traced back to a still-missing closing brace for `Principal`. Root cause on the second pass: the file hadn't been saved after the edit, a real and common mistake worth remembering generally - always confirm what's actually on disk (`cat main.tf`) before re-running commands, rather than assuming an edit landed.

**`terraform validate`**: passed cleanly on the corrected, saved version. Not applied, by design - the ARN itself is fictional, so even attempting `apply` would fail immediately regardless of account structure, making this piece purely a structural/syntax demonstration rather than one that would hit a "real" AWS-side rejection the way the SCP would.

## 2.3c - Identity Center: permission sets

**Design:** two new resource types, distinct jobs - `aws_ssoadmin_permission_set` (a reusable, account-agnostic permission *template*, analogous in spirit to an `aws_iam_policy` but designed for Identity Center's multi-account model, defined with a `session_duration` using ISO 8601 duration notation, `"PT2H"` = 2 hours) and `aws_ssoadmin_permission_set_inline_policy` (the resource that actually attaches real IAM policy JSON - a read-only S3/general allowlist, same spirit as 2.2's boundary - to that permission set, referencing it via `instance_arn` and `permission_set_arn`). Framed conceptually before writing anything: Identity Center solves the problem of defining a person's access *once*, centrally, rather than managing separate IAM users/roles per account - the natural next step in scale beyond everything else built in this portfolio, and arguably the pattern most representative of how a larger organisation like Starling would actually manage human access day to day.

**Real, recurring pattern in the mistakes, worth naming explicitly**: the "list needs an object wrapper" confusion (`Statement = [ Action = ... ]` instead of `Statement = [ { Action = ... } ]`) recurred here for at least the third time across the portfolio (2.2, 2.3's earlier pieces) - flagged directly as a personal recurring slip worth deliberately watching for, since naming one's own repeated mistake is the fastest route to catching it before running `validate` rather than after. Also caught and corrected: resource references mistakenly wrapped in quotes (turning a live reference into a dead literal string - the same "quotes turn a reference into text" error category as very early projects), and a `Version` string typo (`"20120-10-17"`, extra digit).

**`terraform validate`**: passed cleanly for the complete file - all three 2.3 patterns (SCP, cross-account role, Identity Center permission set + inline policy) together. Not applied, by design, same reasoning as the other two pieces: Identity Center isn't enabled in this Free Tier account, and the `instance_arn` is fictional throughout.
